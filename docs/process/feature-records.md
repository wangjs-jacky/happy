# Happy Feature 开发与上线档案

本规范只适用于 Happy/Paws 及其 sibling worktree，不修改全局 Skill、其他项目或其他知识库。功能新增、Bug 修复和影响用户行为的重构都建立 Feature 档案；同一功能的后续修复更新原档案，不重复建同名项目。

## 唯一入口与目录

使用 CLAUDE.md 的 Obsidian 索引路径定位 Happy 项目，在其下使用 `Features/`。沿用已有 `wiki/projects/happy` 的大小写，不再新建平行的 `Wiki/Projects/Happy`。私有事实和本机路径只写 Obsidian；本仓库只保留规范、通用模板和代码测试。

```text
wiki/projects/happy/Features/
  index.md
  Happy功能开发与上线指南.md
  模板/功能档案模板.md
  模板/Ego验收模板.md
  <功能名称>/
    功能说明.md
    讨论与决策.md
    前端设计.md
    代码导读.md
    上线与回滚.md
    会话与证据.md
    测试/
      Ego验收.md
      自动化与运行验证.md
```

每个 Feature 使用稳定 `feature_id`（例如 `happy-codex-account-delivery`）；测试、讨论决定、问题使用 `E2E-001`、`D-001`、`BUG-001`，后续不要重新编号。跨 Feature 只建立链接，证据不复制多份。文档 frontmatter 含 article_id、feature_id、type、tags、created_at、updated_at；索引页可不设 feature_id。

## 在什么阶段更新

| 阶段 | 必须留下的内容 | 可以继续的条件 |
| --- | --- | --- |
| 开始 | 用户原始问题、目标、范围/非目标、Feature ID、验收条件、会话来源 | 先读已有档案，再按当前证据验证；不能把旧结论当本次事实 |
| 讨论 | 提案、理由、用户决定、被否定的假设、未解决问题 | 结论注明“已证实/推测/已否定/待验证”，重要纠正保留旧说法与纠正原因 |
| 设计 | 页面入口、状态、交互、文案、草图/截图/设计稿来源 | 无 UI 改动也写明边界；保留已有设计，不为填表捏造设计稿 |
| 实现 | 正常流程→故障位置→修复方式→边界；关键模块职责与固定 commit 代码链接 | 面向人讲解因果，不只堆文件名；保持 root clean main，代码只在 worktree 改 |
| 验证 | Case、前置状态、操作、预期、实际、证据、环境与 commit | 未跑写未执行，失败留原因；单测/API/日志不得冒充浏览器 E2E |
| PR/上线 | PR/head/merge SHA、CI、目标设备/平台、版本、发布 run、回滚点 | 沿用仓库现有授权和合并门禁；每个交付面分别核对，不把合并等同上线 |
| 收尾/后续 | 剩余风险、负责人/下一步、真实上线状态、索引、证据归档状态 | 输出档案入口和未完成项；更新完成后才能宣称“档案完整” |

每次上线在“上线与回滚”新增发布条目，不覆盖历史记录。区分：实现完成、测试通过、PR 合并、部分设备部署、全部目标部署、真实用户验收。已上线仍可有未验收项，必须显式显示。

## Ego E2E 与测试证据

涉及浏览器的验收只允许 Ego（ego-browser，或 ego-ops 委派 Ego），执行前读取对应技能。桌面/移动端范围按功能需求确定；Tauri 不在本项目支持范围。

`测试/Ego验收.md` 必须记录 Case ID、对应需求/问题、前置账号/设备状态（脱敏）、步骤、预期、实际、结论、验证时间、页面 URL、代码版本和证据索引。一个 Case 一条结果；失败、阻塞、未执行、不适用分别标记。

Ego 执行时按当前 Happy 会话的捕获协议记录 runId、skillName、sessionId、taskSpaceId、targetId 与预期 URL；每个关键步骤只报告一次已验证截图。保留捕获 helper 返回的 receipt 与图片关联，禁止借用别的任务截图。截图采集沿用项目已有用户授权规则，未授权/未采集如实记载，不伪造豁免或新增强制截图审批。

需要远端复看时，视频/图片用 Happy 相应工具交付；只有本机路径的证据标注“仅本机可访问”。没有真实 Ego 验收时可以交付非 UI 修复，但不能写成“E2E 已通过”；说明替代验证与剩余缺口。

## 会话与 JSONL 来源

`会话与证据.md` 记录 Happy session ID、Codex thread ID、本次真实 JSONL 绝对路径、宿主机、已核验时间、关联讨论/问题以及路径是否临时。依据 thread/session 元数据定位，不能靠“最新文件”猜测。同一 Happy 会话如有多段 rollout，逐段登记，缺失写缺失。

JSONL 是原始来源，讨论文档是便于人阅读的摘要。默认只记录地址，不把全量 JSONL、auth.json、token、密钥或账号密码复制进 Wiki/公开 PR。临时路径不是永久归档：在清理 worktree/临时 home 前检查引用；需要持久保留时在私有证据区保存审查脱敏后的材料并更新地址、校验值和保留范围。正在写入的 JSONL 注明“进行中”，不宣称快照完整。

## 交付前人工核对

- [ ] 问题→决定→代码→测试→发布→来源可以互相追溯。
- [ ] 前端设计和代码导读可被未参加讨论的人理解。
- [ ] 已证实、推测、未解决问题没有混写；没有把截图外推为根因证据。
- [ ] Ego E2E 与单测/API/运行日志分开，失败与未执行保留。
- [ ] 每个部署目标有独立状态；未升级设备、未发布 OTA 等已列明。
- [ ] JSONL 来源真实存在或明确标为失效，临时证据保留边界明确。
- [ ] Features/index.md 和 Happy 项目索引有入口，双链可解析。

这是一套项目执行约定，不是自动采集服务。不能声称写入规范后会自动监听/上传全部会话，也不能因未配置 Obsidian 而丢弃已完成工作：先在 worktree 私有临时区保存脱敏草稿，报告待归档，恢复路径后补齐。
