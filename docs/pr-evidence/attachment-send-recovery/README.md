# 附件发送失败恢复验收

修复新建会话上传失败时泄露内部错误码、误报同步失败，以及修改附件后仍重试旧草稿的问题。

## 已完成的验证

- 100 项相关单元、组件和集成测试通过，happy-app typecheck 通过。
- 本地隔离浏览器用例「附件上传失败后保留草稿并在原会话恢复发送」通过。
- 浏览器首次将 request-upload 注入 HTTP 503，核对失败提示、草稿保留及无内部错误码弹窗；恢复后核对进入会话页、仅调用一次创建会话 RPC、上传请求共两次，且服务端存在可解密的对应附件事件。
- 浏览器截图：`case-1-after.png` 为失败保留草稿，`case-1-recovered.png` 为恢复后的会话页。
- 浏览器断言不单独证明消息精确一次提交；完整消息原子性和避免重复发送由同步层及真实 Hook 测试覆盖。
- 故障注入会产生预期开发日志提示。未配置的本地 /logs 收集服务连接失败，不属于生产上传故障；浏览器未捕获未处理页面异常。

## 复跑

通过仓库环境工具准备独立服务与测试账号后，将认证入口及服务地址仅放在环境变量中：

```sh
pnpm --filter happy-app exec playwright test e2e/web-compose-home.spec.ts -g '附件上传失败后'
```

`HAPPY_E2E_WEB_URL` 与 `HAPPY_E2E_SERVER_URL` 必须来自隔离环境。可选 `HAPPY_ATTACHMENT_EVIDENCE_DIR` 保存截图；`HAPPY_ATTACHMENT_EVIDENCE_PHASE=before` 用于在修复前源码上重现旧提示。
